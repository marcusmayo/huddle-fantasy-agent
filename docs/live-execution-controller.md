# Live execution controller remediation

This is an implementation and test record after the first real DR draft. It does not certify a clean next Yahoo draft. The earlier eight-team mock acceptance did not establish reliable operation in the six-team, twenty-round real league.

The [September 9 actual Yahoo acceptance record](yahoo-browser-acceptance-2026-09-09.md) retains two failed attempts. The first stopped before activation with an unexplained route mismatch. After dated candidate preparation, the second activated but timed out reading Results and was explicitly stopped without any Draft or Queue input. It exposed tab-role navigation, short-countdown parsing, invocation-budget and in-app display-reader defects, now locally repaired. Read-only checks recovered all 120 results and showed all fifteen owned picks at 640×720. These checks do not establish continuous manual draft acceptance.

`scripts/live-draft-controller.mjs` contains the maintained execution state machine and a purpose-built Huddle API client. It requires an accepted execution handoff, verified league/team/seat/total picks, protected Yahoo/Huddle roles, a room adapter, a draft-view display adapter, and an optional synchronous choice policy. Without a custom choice it follows the exact-turn Huddle preferred player. An audible policy must return the alternative identity and its reason; the service checks that an audible actually differs from the preferred player. Recording is optional external evidence. No recorder tab, capture health, video file or recording connection is required to start control, recommend players or submit picks.

The controller reads and reconciles the completed board, prepares exact Yahoo identities, obtains a short-lived control lease, and saves the selection plan before recording dispatch. The room adapter must then verify the exact visible numeric player ID, position, league, current owned turn and deadline before one Draft input. A result with the same numeric ID must reconcile before another input is possible. A lost input response stays uncertain even when its resulting player matches; it is not counted as a fully verified manual input.

Before dispatch, `scripts/huddle-draft-display-cua.mjs` verifies that the actual rendered Huddle view shows the matching recommendation revision, preferred player, selected player and reason, with all panels visible and no stale flag. The decision must remain visible for at least 400 milliseconds and then pass a second read. The service requires a recent, matching `display-confirmed` receipt for computer-use submissions so the operator can see the decision. This checks the app's display only and never queries a screen recorder.

Page display reads use document evaluation after an actual in-app BODY locator timeout. Revision waiting, stability and the final read share one deadline; cancellation prevents confirmation. Frame-root support remains scoped to the supplied frame. The controller yields before starting multi-step reconciliation when its remaining window is insufficient and leaves transport settlement time inside the outer watchdog. Status identifies any unsettled operation; it never authorizes a second action behind one.

Lease tokens remain in memory. Every activation creates a new run ID; an old run cannot submit a previously saved plan, even if the controller name is reused. The public control status distinguishes a fresh executing observer from expired, stopped, uncertain or completed control. Fresh observations cannot revive a stopped lease without a newly verified handoff. Opening prepared choices require two distinct, recently observed available Yahoo identities; availability is scoped to the same league, team and current board.

The controller reserves time for dispatch, result inspection and reconciliation. Estimates use conservative minimums and the largest recently measured operation durations with a margin. Individual operations have a bounded response deadline, but the controller also retains an unsettled-operation flag: a timeout does not imply that a browser input was cancelled. No second browser operation begins behind an unresolved operation. `runWindow` processes consecutive turns without returning between them, for a maximum of 45 seconds per call. The invoking computer-use runner must immediately continue the same controller; these windows do not themselves create a persistent background runner.

A window yields before starting a selection if the remaining invocation budget cannot cover the whole operation. This does not create an uncertain pending selection. Browser and server observation clocks allow up to one second of positive skew; observations more than five seconds old or more than one second ahead remain invalid. Deadline calculations subtract one additional second of clock uncertainty. The tolerance fixes a three-millisecond browser/Node discrepancy reproduced during remediation; it is not evidence of the cause of the original pick-84 failure.

## Interruption and handoff

`runWindow({signal})` now treats an aborted invocation as a terminal stop for that controller instance. `requestStop(reason)` prevents new operations immediately, while `stop(reason)` also attempts bounded evidence persistence and lease revocation. They cannot cancel a browser input already issued. An outstanding operation must settle before cleanup begins; `unsettled`, `stopEvidenceSaved` and `stopConfirmed` distinguish local intent from confirmed service outcomes. Cleanup can be retried without resuming drafting. A fresh controller and verified handoff are required afterward.

Before `room.submit` is invoked, the original authenticated controller run may save `input-not-dispatched`. This allows a new reviewed plan after cancellation, even if dispatch intent had already been saved. The event has a stable ID for lost-response retries and remains authenticated after heartbeat expiry. A service restart loses that in-memory authority; a different run cannot invent the old run's cancellation. Once input was issued, the controller saves acknowledgment or uncertainty instead. Those events cannot be converted to no-input cancellation, and takeover requires the accepted Yahoo result to reconcile. Cancelled plans cannot receive credit for independent user or automatic picks.

Overlapping windows and standalone steps are rejected before they can replace an active window's deadline. Browser-context termination is a terminal handoff condition, not a transient read retry. The draft view ages cached controller heartbeats locally, conservatively includes request latency and removes the active claim on request errors or expiry even while the next request hangs. A confirmed cancellation remains visible alongside the reviewed choice; an uncertain submission retains its warning.

A read-only runtime probe on September 8 evening attempted a delayed DOM snapshot after its CUA tool invocation returned. It failed with `node_repl exec context not found`; it made no browser input. This establishes a limitation of the current runtime: retaining JavaScript state does not keep an executable browser context alive. Browser actions must be awaited inside an active supported tool invocation. The bounded controller is not an unattended background service. Uninterrupted invocation, attention handoff and real Yahoo timing acceptance remain open; no scheduler or unawaited promise is accepted as a workaround.

`scripts/yahoo-live-cua-adapter.mjs` contains the browser adapter. It observes visible DOM, resets collapsed searches through the visible clear control, verifies exact numeric player identities, and activates the matching Draft button once with a fresh turn guard. Queue operations verify the before/after identity sets. If a different identity is added, the adapter removes only the newly added wrong identity, verifies restoration of the prior queue, and fails the attempted enqueue. Queue selectors are explicit and still require acceptance against the real Yahoo room. Local simulation is allowed only when the application is explicitly configured for it and the room origin is loopback. A protected Huddle iframe is treated as a distinct surface from its containing room tab.

The Huddle API routes added for the workflow are scoped under `/api/leagues/:leagueId/draft/sessions/:sessionId`:

| Route | Purpose |
| --- | --- |
| `GET /workspace` | Current recommendation revision, reconciled board, audit summary and controller health |
| `GET/POST /controller` | Read health; activate, renew or stop a verified controller lease |
| `POST /decisions` | Save plans, display confirmations, dispatch starts, input acknowledgments, uncertainty, authenticated pre-input cancellation and abandonment |
| `POST /browser-results` | Reconcile a freshly observed complete Yahoo Results prefix after identity and ownership checks |
| `GET /decision-audit` | Export preserved ranking pools, recommendations and chained decision events |

Results reconciliation is idempotent by accepted numeric player identity and pick number. It validates the full submitted prefix before adding picks, then durably saves each new receipt so interrupted reconciliation can resume. It does not submit picks to Yahoo. Input acknowledgment and actual Yahoo acceptance remain separate events, including when polling observes acceptance before the browser response returns.

The draft view at `/draft-view.html?leagueId=…&sessionId=…` displays all three recommendation cards, the selected player and reason, reconciliation receipts, the full owned roster, and feed/controller health. Earlier checks covered 960×820 and 920×820 with automatic timeout recovery and final 120/120 completion. The final computer-use rehearsal ran in an actual 1280×720 captured browser surface, with Huddle occupying 640×720. A compact layout keeps reconciliation and all twenty owned picks together at that size. The completed screenshot was visually checked; each of the twenty decisions also passed the rendered-view check before input. This display is useful with or without an external recording.

Log: `.media-build/controller-interruption-full-suite.log`; fleet-core integrity also passed. The preceding **242-test** evidence-refresh batch is documented in [player evidence recovery](player-evidence-recovery.md). The browser results below remain the earlier, separately scoped CUA acceptance; newer unit/integration tests do not replace live Yahoo or production timing acceptance.

The full local suite passed **234 tests**, zero failures or skips, in 53.9 seconds. Log: `.media-build/postmortem-browser-final-suite.log`. Application-level tests exercise the actual service, leases, audit and browser-results reconciliation using synthetic values and an injected clock. All twenty dispatches follow durable plans; all twenty inputs and accepted identities match; the full audit verifies after restart. Fault cases cover transient browser and Huddle failures, restart and lease expiry, wrong room/turn, insufficient clock reserve, audibles, conflicting accepted results, missing and late input responses, skewed observation clocks, clipped or mismatched displays and short invocation windows. Real wall-clock hangs verify that a timed-out operation cannot overlap a new browser action.

The separate **CUA browser acceptance** used `scripts/live-browser-rehearsal.cjs` and `test/fixtures/live-browser-rehearsal.html`, actual Huddle application services, six teams, seat one, twenty rounds and a 75-second clock. The final narrow-screen run produced twenty acknowledged and matched inputs, twenty fresh recommendation/display receipts, zero simulated autopicks and 120 reconciled results. A deliberate alternative at pick 37 exercised the audible path; that synthetic choice is unrelated to the historical draft's strategic decisions.
